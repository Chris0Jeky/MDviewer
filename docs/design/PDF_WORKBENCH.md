# PDF workbench

Status: **P0 merged (#312); P1a (engine, reading view, PDF tabs; open by drop or the browser file
picker) in progress; P1b (native `.pdf` open, `read_pdf`, Library) next.** P1 is split in two so the
native command lands as its own small reviewable change, announced to the Finish lane. Contract: [2026-11-13 complete push](2026-11-13-complete-push.md),
track P. Baseline: main `e5e96f5`. This file holds the engine evidence, the engine decision (ADR), the
document and save model, the CSP decision, the security rules, the caps and the proof each slice owes.
It prescribes seams and limits, not code. Where it disagrees with the contract, the contract wins and
this file is corrected.

Goal: open a PDF, read it well, change it, and save a valid PDF, entirely locally, on Windows and on
the web, without changing the Markdown reader's cold start or the no-slice export.

## Decision (ADR-P0): one engine, PDFium-WASM

**Context.** The contract requires one engine that both renders and writes ("what you see is what is
saved"), a permissive licence, local execution, incremental saves and true redaction, and it allows a
second engine only for a job the first cannot do.

**Decision.**

1. **Runtime engine: `@embedpdf/pdfium` 2.15.1**, exact pin, loaded only inside the lazy `src/pdf`
   chunk. It renders, extracts text, lists and edits page objects, edits pages, annotations, forms,
   attachments and metadata, redacts, and saves incrementally or in full (E4–E21).
2. **Second parser for tests only: `pdfjs-dist` 6.5.438**, exact pin, `devDependencies`. Every save
   path's tests reopen the output in it (E23). It never ships.
3. **P6 is decided at P6.** PDFium has no raw content-stream or object-dictionary API (E22). P6 starts
   with a half-day spike between (a) a small in-house reader for indirect objects plus an
   incremental-update writer (append new objects, xref section, trailer with `/Prev`), and (b)
   `@cantoo/pdf-lib` as a second engine for that job only. The P6 PR records the choice here with its
   own evidence and round-trips its output through PDFium (the rule for any second engine).
4. **Text editing in place is possible**, so P4 plans the full four-rung ladder, not remove-and-redraw
   only (E9, E10, E13).

**Rejected.** pdf.js as the runtime engine: rendering and writing would be two engines, and its
editor writes annotations, not page content. MuPDF as the core engine: PDFium does P1 to P4 (owner
decision: not revisited); MuPDF is a P5/P6 candidate only (see "Licence decision"). The original `pdf-lib`:
unmaintained and no renderer. A pdf.js renderer plus a pdf-lib writer: two engines for the core path.

**Consequences.** The PDF chunk costs about 2.2 MB compressed on first PDF open (E3); nothing loads
before that. The wasm is fetched from the app's own origin. The licence bundle gains PDFium and its
third-party notices (P1). Font grafting embeds whole fonts until a subsetter is justified (P4 decides,
with sizes).

**Reversible by** swapping the engine module behind `src/pdf/engine.ts`; nothing outside `src/pdf`
calls PDFium.

### Licence decision (owner, 2026-11-13)

The owner accepts AGPL source-offer duties. MuPDF.js (`mupdf`, AGPL-3.0-or-later) may be adopted
wherever PDFium cannot do the job, most likely P6 (raw content streams and object access, E22) and P5

when it does the job equally well; the adopting PR names the capability gain that justifies MuPDF.

## Code layout and seams

- `src/pdf/**` is the only code that knows PDF. One lazy import (`import("../pdf")`) from the shell's
  open path; the Markdown reader, the paginated workspace and their chunks never import it. A
  cold-start test asserts no `src/pdf` chunk and no `pdfium.wasm` request until a PDF is opened.
- `src/pdf/engine.ts`: the only module that calls PDFium (memory, strings, handles, save writer).
  Everything else uses its small typed API.
- **Document kind.** A PDF is an openable kind beside Markdown and the data kinds, decided by
  extension and by the `%PDF-` signature. It is never sent through the Markdown pipeline. It plugs into
  the shell's one document store (`src/desktop/documents.ts`), tabs, Library and command/panel
  registries with wire-up lines only; its view, journal and save logic live in `src/pdf`.
- **Native bytes (Windows).** Two commands, announced to the Finish lane before they land:
  `read_pdf(token) -> bytes` for a file the host opened or the Library holds (same token registry,
  same open-time policy, 200 MB cap), and `save_pdf(token, generation, bytes)` /
  `save_pdf_as(token, name, bytes)` over the existing `replace.rs` primitive with the same conflict
  rules as Markdown. `file_policy.rs` gains `.pdf`. No generic file command; the webview never sends a
  path.
- **Web.** Open through the existing file input and drop; save through the download fallback until
  the Web lane's browser host (W1) lands, then through the same `Host` contract.

## Document, journal and save model

- **Original bytes are kept.** Opening a PDF keeps its original bytes (`originalLength`, SHA-256)
  for the life of the tab. Nothing is written until the user saves.
- **Edit journal.** Every change is a journal entry `{op, page, target, before, after}` applied to the
  live PDFium document. Undo reopens the original bytes and replays entries 1 to *n − 1* in order (E6:
  opening is milliseconds). No partial replay: page moves and deletes change indices, so every undo
  replays the whole journal. Redo re-applies. The journal is in memory only, like Markdown sessions.
- **Incremental by default, for additions only.** A save whose journal only *adds or changes without
  removing* (new annotations, form values, rotations, page moves, new attachments, new metadata values)
  uses `FPDF_INCREMENTAL` (E11): the original stays a byte prefix and earlier signatures stay
  verifiable.
- **Any removal defaults to a full rewrite, said first.** If the journal removes or replaces content
  (retyped text on any rung, removed objects, page deletion, redaction, removed annotations or
  attachments, cleared metadata, repair, compact) the save defaults to `FPDF_NO_INCREMENTAL` (E12,
  E13, E18) and says why before writing: an incremental save keeps the old content readable in the
  earlier revision. The user may still choose incremental for a non-redaction removal; redaction is
  always a full rewrite.
- **Encryption is kept.** Saving an encrypted file keeps its encryption unless the user removes it;
  P2 proves a saved encrypted corpus file reopens only with its password, for both save modes.
- **Revert to original** never truncates or writes in place outside the save primitive
  (`FILE_LIFECYCLE.md`: no truncate-then-write). It is offered only when the bytes on disk begin with
  the recorded original (SHA-256 of the prefix matches). It always confirms that saved edits on disk
  will be discarded, and its default action is "Save the original as a copy". "Revert this file"
  writes the original-length prefix through `save_pdf` and `replace.rs` with the generation and
  conflict checks, like any Save. Without a binding (web download), Revert reopens the original bytes
  kept in memory.
- **Copy by default.** The first save of a PDF in a session is Save As a copy, also on `Ctrl+S`. After
  that, `Ctrl+S` on a bound PDF asks once per session ("Save over the original file?") and then saves in
  place with the Markdown conflict rules (named assumption).

## CSP decision

**`worker-src` stays `'none'`.** PDFium runs on the main thread with no worker (E4, E6): one page
renders in 25–36 ms at 2×, and only visible pages render. `script-src` stays
`'self' 'wasm-unsafe-eval'`; the wasm is fetched from `'self'` (`connect-src 'self'` already allows
it). No CSP change ships with the PDF workbench. If P1's 1,000-page scroll test shows main-thread
jank above budget, moving the engine to a worker is a boundary change with its own evidence and an
extended `tests/desktop-csp.test.ts`; it is not assumed now.

## Security rules

1. **No PDF JavaScript.** Never call `FORM_DoDocumentJSAction`, `FORM_DoDocumentOpenAction`,
   `FORM_DoDocumentAAction` or `FORM_DoPageAAction`. Document-level JavaScript is listed in
   Properties as "contains scripts (not run)".
2. **An allowlist of actions.** Only two actions act: an internal GoTo (a page jump) and a URI whose
   scheme is `http` or `https` (the shell's existing link policy, `external.rs`). Every other action (Launch, remote or embedded GoTo,
   JavaScript, SubmitForm, ImportData, ResetForm, Named, Rendition, Sound, Movie, a URI with any other
   scheme such as `javascript:` or `file:`) is shown with its kind and never followed. The document's
   OpenAction and additional actions are never run.
3. **Embedded files are never opened automatically.** They are listed; saving one is an explicit user
   action through the normal save path. Opening one inside MDviewer is allowed only for kinds MDviewer
   already opens, as a new in-memory document.
4. **External links** go through the existing confirm path (`native.external` on Windows, the web's
   confirm and `noopener` on the web). Internal destinations jump in the view.
5. **Passwords** live in memory only, for the tab's lifetime; never persisted, logged, sent to
   Pulseboard or placed in a URL. Saving keeps the file's encryption unless the user removes it.
6. **Parsing is untrusted input.** The engine runs inside WASM memory; a failed open or a WASM trap
   (including out-of-memory) is an error state with a code that closes only that PDF. The caps below
   bound bitmaps and heap. A main-thread hang inside PDFium cannot be interrupted; that residual risk
   is accepted for P1 and is the trigger for the worker decision in "CSP decision". Names that come
   from the file (attachments, titles) are display text only and are sanitised before being offered
   as a save-name suggestion (path separators, control and reserved characters removed, length
   capped). Pulseboard events carry closed enums and buckets only.
7. **Redaction claims are exact and scoped.** The claim is "text removed": glyphs inside the
   redaction areas are deleted from the content stream (E13). "Redacted" is shown only after a full
   rewrite and a scan of the saved raw bytes *and* every inflated stream finds no match. Redact also
   removes matches from annotation contents, bookmark titles and Info metadata. What it does not
   cover is said in the dialog: text drawn as images or vector outlines, XMP metadata, attachments,
   form field values and structure-tree alternate text under the area. P4 either clears those (XMP
   and attachments need P6's object access) or keeps the warning.

## Retype ladder (P4) mapped to the engine

1. **In place:** `FPDFText_SetText` then read back with `FPDFTextObj_GetText`; equal means every glyph
   exists (E9, E10).
2. **Font graft:** find a full font by PostScript name among the document's embedded fonts
   (`FPDFFont_GetFontData`), installed fonts (Local Font Access where granted) and bundled
   metric-compatible open fonts; load with `FPDFText_LoadFont` and redraw the changed run (E19).
3. **Fit or reflow:** character spacing or horizontal scale within ±3%, else re-break the paragraph
   inside its original box; overflow is reported.
4. **Remove and redraw:** `EPDFText_RedactInRect` or `FPDFPage_RemoveObject`, then a new text object at
   the same matrix (E13). Also the redaction path.

The UI states which rung was used for each edit.

## P7 (scans) decision note

Out of scope for this push. Starting it needs an owner decision on a model-download policy: an OCR
engine (for example Tesseract compiled to WASM, Apache-2.0) adds roughly 10–20 MB of language data per
language, which the offline app would have to bundle or fetch once with consent. Until then a scanned
PDF opens, renders and can be annotated, and the UI says that its text cannot be edited because the
page has no text layer.
